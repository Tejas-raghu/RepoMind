## Day 9.5A — hybrid search verified

- Diagnosis on repository 38: chunk 556 (`TaskTrail/src/services/apiClient.ts`, lines 1–44) contains the stored `Authorization`/`Bearer` header assignment. Unfiltered vector Top-20 ranked `README.md` #1 at 0.358006 and `apiClient.ts` #3 at 0.318514. The 0.35 cutoff excluded the implementation before Top-K; ingestion and context formatting were not the cause.
- Added `POST /api/repositories/{repositoryId}/hybrid/search` without changing the existing search or RAG context endpoint responses. Vector and lexical candidate searches each default to 15 per repository and model. The vector candidate search has no similarity cutoff. The lexical search uses PostgreSQL `simple` full-text search over content and path, plus case-insensitive literal matching of technical terms, with matching code files ranked before docs. Results are fused by chunk ID using `1/(60+rank)` from each list and return up to five by default, including ranks and scores.
- On four explicitly labeled TaskTrail questions, expected files were `apiClient.ts` (Bearer header), `guards.ts` (protected routes), `outletMarkers.ts` (Leaflet markers), and `AuthController.cs` (JWT validation). Unfiltered vector-only Hit@1 was 2/4 and Hit@5 was 4/4; hybrid Hit@1 and Hit@5 were both 4/4. For the Bearer question, `apiClient.ts` moved from vector rank 3 to hybrid rank 1 (lexical rank 1), while `README.md` moved from vector rank 1 to hybrid rank 2.
- Local HTTP elapsed times for the four hybrid requests were 5,533 ms, 78 ms, 132 ms, and 42 ms in that order; a subsequent warm Bearer request took 143 ms. The first call includes local embedding-model startup and should not be treated as a search-only latency measure. The unfiltered vector requests took 6,120 ms, 170 ms, 42 ms, and 83 ms in the same order; these are small, sequential local observations, not a benchmark.
- `dotnet build backend/RepoMind.Api/RepoMind.Api.csproj --no-restore -p:UseAppHost=false -p:OutputPath=bin/Day95/` succeeded with zero warnings and errors. `dotnet test tests/RepoMind.Api.Tests/RepoMind.Api.Tests.csproj --no-restore -p:UseAppHost=false -p:OutputPath=bin/Day95/` passed all 59 tests, including RRF ordering/deduplication, no-cutoff candidates, exact technical terms, path matching, repository isolation, and empty/missing repositories. Live checks returned HTTP 400 for invalid ID, blank query, and `topK: 21`, and HTTP 404 for an unknown repository.
- Limits at initial Day 9.5A verification: this four-question synthetic evaluation is too small to establish general retrieval quality. The lexical query scans small repositories without a text-search index; term extraction is English-oriented and code-file preference may over-rank an irrelevant file. At that point `/rag/context` still used semantic retrieval.

## Day 9.5C — evidence verification, verified implementation

- Added `POST /api/repositories/{repositoryId}/rag/verify` after the existing repository-scoped hybrid/RRF/optional-reranking path. It sends up to five complete chunks to local Qwen with a bounded prompt and JSON Schema. The service validates status and evidence IDs; the response builds source paths and line ranges only from retrieved database records. No final answer is generated.
- Empty retrieval returns `insufficient_evidence` without Qwen. A chunk that cannot fit the configured verification budget is not silently truncated. Model timeout, unavailable model, malformed output, or invalid IDs returns `verification_unavailable` with `answerable: false`. The returned reason is a fixed safe explanation rather than model text.
- `dotnet test tests/RepoMind.Api.Tests/RepoMind.Api.Tests.csproj --no-restore -p:UseAppHost=false -p:OutputPath=bin/Day95C3/` passed 96 tests, including PostgreSQL repository-isolation and foreign-ID rejection. `dotnet build backend/RepoMind.Api/RepoMind.Api.csproj --no-restore -p:UseAppHost=false -p:OutputPath=bin/Day95CFinal/` succeeded with zero warnings and errors.
- Live HTTP checks on the new endpoint returned 400 for invalid ID and blank query and 404 for an unknown repository. On repository 38, a five-chunk Bearer request returned `verification_unavailable` after a 60-second verifier timeout; a three-chunk Bearer request completed in about 40 seconds but returned `insufficient_evidence`, a false negative for the known `apiClient.ts` implementation chunk.
- A versioned ten-question TaskTrail smoke set and PowerShell measurement script are under `evaluation/`. These are small local checks, not reliability evidence.
- On a completed ten-question local run with `topK: 3` after putting the short evidence reason before status in Qwen's JSON schema, status-level supported acceptance was 5/5, unsupported false acceptance was 0/5, uncertain count was 0, verification-unavailable count was 0, and average verifier duration was 49,629 ms. The table shortened evidence paths; one route-guard decision visibly cited `README.md` rather than `guards.ts`. A separate repeat of the backend-login question cited frontend `authService.ts` rather than the backend handler. Thus status-level acceptance overstates correctly sourced evidence. The final prompt added an explicit distinction between implementation code and README/frontend calls, but a subsequent full run stalled in a local Ollama call and was stopped; final-prompt ten-question rates are unmeasured and no complete result file was produced. These observations do not establish general reliability.

## Day 9.5 unified RAG flow — verified implementation

- `/rag/context` now uses one repository-scoped retrieval pass: vector and lexical candidates, RRF, optional local reranking, then evidence verification. It formats only validated evidence IDs in the final rank order. `/rag/verify` uses the same retrieval and verification path. Verification is required for every `/rag/context` request with retrieved chunks; empty retrieval skips the model.
- `Reranking:Enabled` is now true in `appsettings.json` so the configured API runs the full flow. It can be turned off without bypassing RRF or verification. If verification is insufficient, uncertain, or unavailable, the context contains no source blocks. If verified code cannot fit the RAG context budget, the context is empty and the response marks the decision uncertain.
- `dotnet test tests/RepoMind.Api.Tests/RepoMind.Api.Tests.csproj --no-restore -p:UseAppHost=false -p:OutputPath=bin/UnifiedFlow/` passed all 96 tests, including a PostgreSQL integration test of reranked candidate order reaching verification, trusted source selection, repository isolation, one embedding pass, empty repositories, unavailable verification, and context budget handling. `dotnet build backend/RepoMind.Api/RepoMind.Api.csproj --no-restore -p:UseAppHost=false -p:OutputPath=bin/UnifiedFlowFinal/` succeeded with zero warnings and errors.
- One live local `/rag/context` request for the Bearer question in repository 38 with `topK: 3` took 187,362 ms. Reranking timed out at its configured 120 seconds; verification then timed out at 60 seconds. The response reported `rerankingStatus: timeout`, `verification.status: verification_unavailable`, `answerable: false`, and zero source blocks. This confirms the failure path is closed but does not demonstrate a successful live rerank or verified answer. Local model latency remains a practical limitation.
